OMEN 17-cb0xxx · board 8603 · field notes

The 45 Watt Ceiling

Everything the Linux side can measure, and the one number only Windows can settle.

i7-9750H RTX 2080 BIOS F.53 kernel 7.1.9-arch1-2 2026-08-29
44.8watts sustained

Under 60 seconds of 12-thread load, this machine settles at 44.8 W in every thermal profile. Performance minus balanced is −0.1 W. Two performance runs agree to 0.1 W.

Before that it boosts to 84–88 W at 4.00 GHz for 10–16 seconds, governed by PL2, then steps hard to 45 W with PL1 as the limiter. That boost is where the retracted “88 W performance mode” figure came from.

Nothing reachable from the operating system moves the sustained number.

What the profile actually changes

ProfileMSR 0x610 PL1MMIO 0xFED159A0 PL1EC[0x29]Delivered

performance90 W90 W0x0144.8 W

In performance mode both power-limit registers read 90 W and the package still delivers 45 W, so min(MSR, MMIO) does not explain it either. The MSR is inert in both directions — forcing PL1 down to 30 W under load changed nothing. The MMIO copy never moves at all. MSR 0x64F names PL1 as the active limiter throughout, whatever the registers say.

Settled along the way

Two genuine driver bugs, both fixed and installed via DKMS. First, hp-wmi seeds the profile from ec_read(0x95), but on this board that offset holds an ASCII string, so it read 0x37, returned -EINVAL, and disabled platform_profile silently because the setup return value is discarded. Second, the firmware echoes every profile write back as an Fn+P keypress, which the driver turned into platform_profile_cycle() — a feedback loop measured at roughly 900 profile changes per second.

Running your ec-calibrate diff from Linux — finally possible once the driver could switch modes — found the real thermal profile byte at EC[0x29], holding 0x02/0x00/0x01 for cool/balanced/performance. No other EC byte tracks the mode.

And the premise itself is shaky: FINDINGS.md §5c says outright, “Still unmeasured: actual package watts per mode.” The 90 W target is a ThrottleStop .ini setting, never a measurement. The Windows evidence for performance mode is clock-only — 3.59 vs 3.01 GHz — and an FP load at 45 W runs at about 3.4 GHz on this machine.

What to collect in Windows

1

Sustained package power, per mode

decisive

Install HWiNFO64, start it in sensors-only mode, and log to CSV.

  • Set OMEN Gaming Hub to Performance. Run Cinebench R23 multi-core, or Prime95 Small FFT, for at least 5 minutes.
  • Repeat on Balanced.
  • From each log, read CPU Package Power averaged over a window starting 60 s after the load begins — never the first 20 s.
  • Also note: CPU Package Power Limit 1 and Limit 2, CPU Package temperature, average core clock, and the Power Limit Exceeded yes/no flags.
Why it decides everything. Linux sustains 44.8 W in every mode. If Windows performance mode also sustains about 45 W, this laptop is a 45 W machine by design, both hypotheses below die, and the investigation closes. If it sustains 65 W or more, something in the HP stack does something we have not found — and tasks 4–6 become the hunt for it.
2

Power adapter rating

Read the wattage printed on the brick, and check what the machine thinks is attached.

  • The label on the adapter itself — the 17-cb0 with an RTX 2080 normally ships a 200–230 W supply.
  • In HWiNFO, look for a Smart Adapter or AC adapter field, and note anything it reports about rated wattage.
Why. A hard clamp at exactly the CPU’s 45 W TDP, with 39 °C of thermal headroom and no register explaining it, is exactly what an EC does when the supply is undersized. If you are on a lower-wattage or third-party adapter, that is very likely the whole answer. Linux cannot read this.
3

What the dGPU is doing

During the CPU-only load from task 1, record the GPU’s state in HWiNFO: GPU power draw, whether it is asleep or powered.

Why. On Arch the RTX 2080 never powers down — Runtime D3: Disabled by default, idling at 7.85 W. If Windows parks it properly and the EC hands out a shared CPU+GPU budget, an always-on GPU could be why Linux gets pinned at 45 W. Comparing the two states tells us whether that is worth chasing.
Stop here if task 1 shows ~45 W

That result closes the question, and tasks 4–6 are wasted effort. Only continue below if Windows sustains meaningfully more power than Linux does.

4

A WMI trace taken during load

conditional

Clear %LOCALAPPDATA%\HPOMEN\HPOMENBG_*.log, switch to Performance, then run the load for two full minutes and capture the log.

Why this differs from what you already captured. The original trace was taken while clicking through modes, almost certainly at idle. Every command in it has now been replayed from Linux and none of them lift the clamp. If OMEN sends something 15 seconds into a sustained load — when the EC would be applying the clamp — that command has never appeared in any capture we have.
5

EC dump under load

conditional

With RWEverything, dump embedded-controller offsets 0x00–0xFF in Performance mode while the load is running. A second dump on Balanced makes it far more useful.

Why. Direct comparison against the Linux dumps. We know EC[0x29] is the profile byte and that no other byte tracks the mode at idle. If Windows sets some additional EC byte under load that Linux never sets, that byte is the lever.
6

The two registers, read in Windows

conditional

In Performance mode under load, capture both:

  • MSR 0x610 — ThrottleStop’s TPL window shows PL1/PL2 directly.
  • MCHBAR + 0x59A0, physical address 0xFED159A0 — readable in RWEverything’s memory view.
Why. Straight comparison with the Linux values in the table above. If Windows shows something different in either register while sustaining more power, that is the mechanism, in one line.
